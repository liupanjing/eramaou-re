# 角色口上创作任务书

本任务书与 [character_voice_tasks.json](../content/character_voice_tasks.json) 配套，供外部 agent 创作、复核和扩写角色口上。JSON 已包含原文、角色依据、目标位置及独立草稿栏，交回后可以校验并生成待接入的 JSON 和原生 Emuera 文本。

登记日期为 2026 年 10 月 18 日，基于 `dev/non-nsfw` 分支。游戏继续使用 Emuera1824cn.exe。本包不修改玩法、事件条件、角色身份或存档结构。

## 覆盖范围和任务状态

当前有 723 个工作项：319 项基础口吻、348 项事件反应、56 项选项故事。其中 6 项仅作参考，717 项允许填写草稿。

这些位置已经有文本，是完整的复核与扩写目录，不是 723 处已确认缺文。不要求把已有文本全部重写。角色人格不符、阶段语气混用、模板痕迹明显或变体不足时，再提出替换或新增变体；可保留的条目维持 `pending`，或用 `deferred` 并注明原因。

| 状态 | 用途 | 是否参与候选合并 |
| --- | --- | --- |
| `pending` | 尚未处理，默认 `draft: null` | 否 |
| `draft` | 已填完整草稿，尚未交付 | 否，但会校验草稿 |
| `ready` | 作者完成自检，提交接入复核 | 是；不等于已经通过人物与剧情审阅 |
| `deferred` | 暂缓处理，在 `notes` 中说明 | 否 |

`reference_only` 项目不能填草稿。`legacy_inventory` 只登记旧文件及函数位置，不能作为写入目标。敏感遗留内容只保留覆盖状态与来源，不在本包中提供续写任务。

## 发给其他 agent 的操作要求

可以将本任务书与配套 JSON 一起交给作者，并指定角色或任务编号。JSON 内已有原文；精确核对原设仍需要项目源码，尤其是 `profiles[].evidence` 指向的文件。没有源文件时不得假装已经读过，不能依据角色名字补造传记。

1. 在 `tasks` 中找到分配的任务，阅读 `owner`、`conditions` 和只读的 `current`。
2. 将整个 `current` 对象复制到 `draft`，在 `draft` 中写作。这里需要真正的 JSON 对象，不是包含 JSON 的字符串，也不是 Markdown 正文。
3. 只修改 `status`、`draft`、`author`、`notes`。不要修改编号、目标路径、原文、哈希或元数据。
4. 草稿必须完整保留该任务要求的阶段和字段。未修改的部分也要保留，不能写“同上”或留空。
5. 在 `author` 填作者标识，在 `notes` 写修改理由、依据及需要接入者注意的问题。完成自检后将状态设为 `ready`。
6. 交回有效 UTF-8 JSON。不要把整个文件包在代码围栏里，也不要加入 JSON 注释。

可以只保留自己负责的 `tasks` 子集，其他元数据保留不动。校验支持子集交付；合并多个作者文件时按任务 `id` 去重，同一任务有多个版本时先人工选择，不能靠排列顺序覆盖。

建议按角色分配作者，按事件类型作第二轮复核，避免同一人物的初见、日常和战斗台词由不同作者各写一套人格。

完整包约1.6 MB。若只分配白梅花，可从当前源码另导出一份27项的小包：

```powershell
python tools/character_voice_handoff.py --export ../白梅花口上任务.json --owner 170
```

其他角色使用下表配置ID。共用故事使用 `--owner common-0`、`common-1`、`common-2` 或 `common-3`。小包沿用相同任务编号、校验及候选生成方式。重新导出基于当前源码，不会自动复制完整包中尚未接入的草稿。

## 基础口吻任务

以下字段在每份配置中各有一项任务，草稿对象保留 `0`、`1`、`2`、`3` 四个键，每个值为非空字符串数组。可以增加数组中的变体，但每条应有实际区别。

| 字段 | 使用位置 | 写作要求 |
| --- | --- | --- |
| `intro` | 初次实际交谈 | 独立初见；不能假定已有旧经历或亲近关系 |
| `greeting` | 再次来访 | 可以表现见过，但不凭空指认某段已完成故事 |
| `daily` | 日常话题 | 关注具体事情，提供有差异的变体 |
| `positive` | 日常积极回应 | 表达接受本次回答，不提前宣布加入 |
| `neutral` | 日常中性回应 | 保留具体的疑虑或未谈清事项 |
| `negative` | 日常消极回应 | 保留人格；拒绝不必一律辱骂 |
| `address` | 对魔王的称呼 | 只填称呼，如“你”；不加引号、地文或完整句子 |
| `voice` | 不依赖具体旧经历的招呼 | 能在缺少话题历史时成立 |
| `delivery` | 物资实际交付之后 | 确认这次交付，不等同于购买效忠 |
| `reserved_greeting` | 低信任部下来访 | 仍是部下，有保留而不重置成刚被俘 |
| `reserved_daily` | 低信任部下日常 | 保留已发生经历、任命与承诺 |

四态分别是抗拒被俘、仍有戒备、有条件合作、正式归顺。“是否初见”另由 DP_MET 判断，不能以阶段代替见面次数。低信任覆盖字段虽然在 JSON 中保留四态结构，实际显示服从运行时分支，不代表每一态都有独立入口。

## 事件反应任务

每个任务的 `conditions` 已写入入口。不要为未定义的阶段增加键。每态至少保留两条变体，文本只描述实际事件及人物反应。

| key | 场景 | JSON 阶段 |
| --- | --- | --- |
| `attack` | 实际攻击者的反应 | 0、1、2、3 |
| `victory` | 实际获胜者的反应 | 0、1、2、3 |
| `arrival` | 进入地下城的反应 | 0、1、2、3 |
| `join` | 已成功正式加入 | 3 |
| `home` | 已成功迁居 | 3 |
| `job` | 已成功任职 | 3 |
| `job_clear` | 已成功解除职责 | 3 |
| `rest` | 当前设施的一名在场者回应休息 | 0、1、2、3 |
| `world_end` | 征服人间后的反应 | 0、1、2、3 |
| `realm_end` | 其他领域结局的反应 | 0、1、2、3 |
| `castle_fall` | 魔王城陷落后的反应 | 0、1、2、3 |
| `normal_end` | 长期结局的反应 | 0、1、2、3 |

从 `join` 开始的城务与结局事件，在第3态中，数组下标0留给低信任部下的保留语气，下标1起用于通常部下。不要把每个变体都写成亲近状态。攻击、胜利和进入地下城不使用该低信任变体约定。

身份、年龄和在场限制仍由代码决定。玛奥、菲娅的 `join`、`job`、`job_clear` 共六项不接受草稿。结局反应不能让俘虏自动变成部下，也不能把远方胜利写成全城已经搬迁。

## 选项故事任务

每项 `STORY` 是一整段已有事件，包含标题、开场、两轮选择、过渡和结束。只填写完整事件对象。

- 可修改：`title`、`body`、`bridge`、`ending`，以及 `first`、`second` 内的 `text`、`reply`。
- 不可修改：数值效果、字段、每轮选项数量、选项次序及选项原本的立场。两个回合各保留三个选项。
- 四态正文保留四态；第3态重谈旧事，不能再次完成物资交付、收费或正式加入。
- 选项编号已用于存档回顾。即使数值不变，不能将原本拒绝的选项改成赞同，也不能交换两个意思相近的选项。
- 状态字典内可以增加段落；保留外层结构，不自行增加选择回合或新的机制字段。

校验工具能发现结构、占位符和数值变动，不能自动判断人物是否符合原设、选项语义是否被调换。这些需要接入前人工复核。

## 占位符和文字格式

只使用 `{name}`、`{master}`、`{self}`、`{address}`。不要手写内部 `__NPC_NAME__` 等标记。

每个字符串是一条显示文本，不包含实际换行、控制字符、百分号或额外花括号。需要多段时放入数组。保留原作的自称、称呼、语尾和叙述节奏；人格与态度分别处理，不把归顺者统一写成同一种口吻。

不得通过对白虚构尚未实现的系统收益、已经重逢的人物、已确认安全的亲人或未兑现的承诺。家属与年幼角色只作适龄的普通生活交流。临时来访不是永久迁居，数值达标不是已经正式加入。

## 校验和候选生成

在项目根目录执行：

```powershell
python tools/character_voice_handoff.py --validate content/character_voice_tasks.json
```

该命令检查任务目标、原文版本、草稿结构及文字格式，再使用三个现有生成器编译候选。`draft` 状态会校验但不参与候选合并；只有 `ready` 会合并。原文在任务发出后改变时，会拒绝有草稿的过期任务，避免覆盖新版本。

作者交付后，在一个全新的项目外目录生成候选：

```powershell
python tools/character_voice_handoff.py --stage content/character_voice_tasks.json --output-dir ../口上接入候选-第1批
```

输出包括四份 `content` 源 JSON、三份生成 ERB，以及记录实际参与合并任务编号的 `handoff_result.json`。目标目录必须位于项目外且尚不存在，避免游戏加载重复函数。工具不会修改正式的 `content/` 或 `ERB/`。

接入者随后检查候选差异、选项语义和人物表现，再将经过审阅的源文件与生成文件一起纳入开发分支，并按变更范围执行原引擎测试。静态校验成功不等于实际游戏流程已经验证。

若需要基于更新后的源码重新导出，请使用新文件名，工具不会覆盖作者已填写的交付包：

```powershell
python tools/character_voice_handoff.py --export content/character_voice_tasks_next.json
```

不要直接覆盖旧包。对照任务编号把仍适用的草稿移入新包的 `draft`，保持新包的 `current` 和哈希，再重新审阅和校验。已接入项目的内容应记录到开发日志，不能仅以旧包中的 `ready` 当作已完成接入。
