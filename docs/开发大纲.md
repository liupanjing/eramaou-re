# 魔王城重构开发大纲

版本：讨论稿 v0.1。更新日期：2026年10月24日。

本大纲用于确定游戏方向、开发顺序和验收边界。后续以任务编号追踪工作；[开发日志](开发日志.md)记录每次变更，[魔王城模块](魔王城模块.md)等文档保存实现细节。当前先讨论大纲，不继续增加玩法。

## 一 游戏定位与核心循环

玩家扮演魔王，经营一座有人物生活和关系发展的魔王城，与冒险者相遇、发生冲突、交流并推进个人故事，逐渐扩大势力，最终完成世界征服。保留原作的成人向定位和原有养成玩法，使用原 Emuera 引擎。

城务、设施、经济和战争都要服务于这条循环：

**安排城内生活 → 遭遇冒险者与外部冲突 → 互动及个人剧情 → 人物作出关系与立场选择 → 人员参与城务和远征 → 世界局势变化 → 新人物与新事件进入魔王城。**

设计时回答三个问题：玩家为什么要做这件事；它怎样改变人物或魔王城；结果如何回到下一天的游戏中。只有资源增加、设施升级或数字变化，不能单独视为循环完成。

已确认的原则：

- 保留 Emuera，逐步重构，已有角色与存档兼容纳入验收。
- 魔王可以选择设施，在实际地点遇见人物并进行互动。
- 角色的身份、居所、岗位、当前地点分别记录。
- 归顺、工作关系、信任、好感和恋爱关系不能相互替代；恋爱关系需要独立剧情确认。
- 主要角色保留原作人格、背景与称呼。普通人物可以使用性格和出身模板。
- 正文与流程分开，作者可以填写内容；缺稿不能伪装成已发生的事件。
- 每次完成一段可验收的体验，再扩大人物和系统覆盖。

当前分支为 `dev/non-nsfw`，初始提交为 `f6d65c1`。后续新增经济、相处、移动、创作交付工具与本大纲集中收录为一次BASE-02开发快照，提交标题为 `BASE-02: checkpoint castle systems and development roadmap`，可通过Git历史查找。这是当前实现的版本基线，各模块仍按下表分别验收，不补造历史上的分阶段提交。

## 三 开发顺序与里程碑

### M0 确定规则并整理基线

先确定玩家的一天、人物关系的含义、设施分工和本阶段保留范围。把现有改动登记为保留、调整或暂缓，之后再安排基础快照和功能提交；本稿不自动提交或回退代码。

验收：能说清一个时段可做什么、哪些行为消耗行动、人物为何出现在某处、一次互动改变什么；每个已有模块都有处理决定和任务编号。

### M1 打磨城内生活的一天

统一“查看名册、寻找人物、前往设施、进行互动、查看结果、进入下一时段”的体验。先验证当前日程和设施入口是否好找、好用，再决定要不要增加更细的时间或移动。

验收：玩家不读代码也能找到一个人物，在现场完成互动，看见结果并在下一时段找到其新位置；身份、岗位、居所和出勤不会互相覆盖。

### M2 完成一个人物章节

先选择一名成年主要角色，梳理原作背景、初见处境、阶段态度、普通相处、分歧、拒绝与后续回应。用一条有前因后果和阶段结尾的个人事件链，验证关系推进方式，再推广到其他主要角色。

验收：人物能记住关键选择；称呼和态度有依据地变化；拒绝有实际意义；关系确认依赖明确事件；初次、重访与结束后的日常有区别。完整恋爱线不能仅靠把好感刷到阈值实现。

正文创作与系统接入分别记录进度。当前通用普通事件原型不等于这条人物章节已经完成。

### M3 打磨支撑生活与出征的经营

从住房、生活供给、人员职责和远征准备四种需要倒推经济规则。复核已经写入的资源、设施、研究与维护，逐项决定保留或简化，不预设现有整套规则都会留下。

验收：每个保留资源和岗位都能说明用途；日常操作负担可接受；玩家能够判断缺少什么、怎样解决，以及经营决策怎样影响生活或出征。完成一段从正常供给到短缺、恢复的试玩。

### M4 接通人物与世界征服

梳理原版出征与战斗入口，确定人员如何参与、城内安排如何支持、战果如何带来领土变化、人物遭遇和后续事件。优先复用原版可用流程。

验收：打通“准备一次行动、出征、获得明确结果、回城处理后果”的流程。战果必须有可见反馈，不能只回填一笔资金或一个兵力数字。

### M5 补全主线并扩展角色

整理世界势力、章节目标、主要角色介入点、狂王线断点及结局条件。先确定狂王本尊、葵希罗和现有分身内容之间的设定关系，再修补剧情。

验收：主线有明确前置、过程和结果；关键人物的出场与去向能够解释；结局依赖可追踪。主要角色的内容按逐人清单推进，不以通用回退覆盖宣称全部完成。

以上顺序表示优先级，不是工期承诺。完成一个里程碑后再确定下一阶段的具体任务范围。

## 五 追踪与变更规则

每次只推进一个明确任务或其中一个可验收子项。开始前写清“目的、范围、预期体验”，完成后登记“改了什么、怎样试玩、验证结果、剩余问题、对应提交”。

任务记录沿用以下格式：

```text
任务编号：
本次目标：
本次范围：
预期玩家体验：
改动文件与内容任务：
自动验证：
人工试玩步骤与结果：
遗留问题：
提交：未提交／具体提交号
状态：
```

开发日志必须引用任务编号；涉及玩家可见规则时，同时更新本大纲的对应决定。后续提交按任务组织，不再把多个新系统长期混在一个工作区里。现有大批未提交改动先由BASE-02单独整理，不能假装它们已经有历史上的独立提交。

新增系统、改变核心规则或扩大当前里程碑范围时，先更新讨论稿；已明确的任务内修复继续正常推进。程序通过测试时登记技术结果，用户认可体验时再登记试玩验收。缺正文、通用回退和未接通入口分别记录。

## 六 这次先讨论的决定

1. **一天怎样玩：** 暂以原版上午／下午、每时段3行动为讨论基线；设施移动免费，认真互动结算行动。是否好玩在M1通过实际试玩判断。
2. **先打磨谁：** M2只选一名成年主要角色完成章节，再扩大覆盖。选择前先核对她的原作设定和现有内容。
3. **经济保留多少：** 已实装规则暂存，先列用途与取舍；本稿不视为全部认可，也不自动删除现有实现。

上述决定明确前，下一步仅推进BASE-01的大纲讨论，不继续增加系统或批量内容。
